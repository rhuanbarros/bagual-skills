# Decision Log — bagual-worktree-creator

## Session 2026-07-02 (edit) — session-boundary fix

**Problem observed by the operator, live, in a separate conversation:** after creating the worktree, the agent tried to keep implementing in the *same* conversation by `cd`ing into the new worktree's path via a shell tool call. It believed it was now "in" the new worktree because the shell's cwd showed the right path — but subsequent work (edits, further shell calls) kept landing in the original checkout instead, invisibly. The operator had to catch this manually and redirect.

**Confirmed against this skill's own build history.** This exact failure mode happened while building this skill in the first place: the build was intended to happen inside a worktree (session had called the harness's `EnterWorktree`), but every file was written using an absolute path rooted at the *original* checkout, and the resulting files were only ever found in the original checkout — never in the worktree — despite the shell's cwd appearing correct throughout. Two independent occurrences of the same failure, in two different sessions, is enough to treat this as a structural gap rather than a one-off mistake.

**Decision: SKILL.md's final step is now an explicit stop-and-hand-off, not a report-and-continue.** Added to `## Report, Then Stop`: the agent must state plainly that it cannot reliably continue in the current session, and must give the user a ready-to-paste continuation prompt for a fresh session opened directly in `{dest}`. Rejected alternative: instruct the agent to just "be careful with paths after cd'ing" — this is precisely the kind of judgment call an LLM will not reliably get right without being told, since the shell tool itself reports the cd as successful and gives no signal that other tools didn't follow.

## Session 2026-07-02 (build)

**Origin.** Built from lessons learned live in an Epic 32 pipeline session: the operator asked for a worktree "separada a partir do estado atual" (based on current state) to continue epic work in a second VS Code window. The first attempt used the harness's `EnterWorktree` tool with its default base-ref behavior and only carried git-tracked history — the operator then had to explicitly ask "can't you copy all necessary files to have a worktree perfectly equal to the main?" before `node_modules`, `.venv`, env files, and other gitignored runtime artifacts were copied over. This skill exists so that gap doesn't have to be rediscovered per-session.

**Decision: create the worktree via plain `git worktree add`, not the harness's `EnterWorktree` tool.** `EnterWorktree`'s base ref is governed by a global `worktree.baseRef` setting (`fresh` branches from `origin/<default-branch>` by default; `head` branches from local `HEAD`) and isn't controllable per-invocation. In the source session, `fresh` happened to be correct only because local `main` was coincidentally already in sync with `origin/main` at that moment — if the source checkout had unpushed commits, the resulting worktree would have silently missed them, directly contradicting "based on current state." Pinning to `$(git -C {source} rev-parse HEAD)` via a plain `git worktree add` is deterministic and doesn't depend on that setting. Rejected alternative: instruct the agent to "check the baseRef setting first" — more moving parts for the same guarantee, and the setting isn't inspectable from inside a skill.

**Decision: replicate BOTH gitignored artifacts AND uncommitted working-tree state.** The triggering conversation only needed the first half (the source checkout was fully committed at the time), but "a worktree identical to what I have right now" logically includes uncommitted edits too — `git worktree add` never carries those, and silently dropping a half-finished edit would be a worse failure than the one that prompted this skill. `scripts/copy_ignored_artifacts.py` applies `git diff HEAD` as a patch to the destination and copies `??` (untracked, not-ignored) files, in addition to the ignored-artifact copy. If the patch fails to apply, the script preserves it on disk (`patch_saved_at`) rather than discarding it, and SKILL.md requires surfacing that to the user explicitly.

**Decision: hardlink by default, real-copy fallback on `OSError` (cross-device).** In the source session, `node_modules` (513M) + `.venv` (227M) copied instantly via `cp -al` because both checkouts shared a filesystem (`.claude/worktrees/*` nests under the same repo). Hardlinks cost zero extra disk and zero copy time, so they're the right default; a plain `shutil.copytree`/`copy2` fallback keeps it correct (just slower) if the destination ever lives on a different mount.

**Decision: noise exclude list is a maintained deny-list in the script, not a prompt-level judgment call.** The source session hand-picked what to skip (`__pycache__`, `.pytest_cache`, `.coverage`, `.playwright-mcp/*` logs, `_bmad-output/test-artifacts/*`, `.claude/scheduled_tasks.lock`) versus what to keep (`node_modules`, `.venv`, env files, `supabase/.temp`, `qa-pack/access/*`). That triage is exactly the kind of "would an LLM get this right without being told" gap — an LLM re-deriving it from scratch each time is exactly how the first attempt in this project missed the copy step entirely. Baked into `BASENAME_EXCLUDES` / `PATH_PREFIX_EXCLUDES` / `COMPONENT_EXCLUDES` in `copy_ignored_artifacts.py` as generic, project-agnostic patterns (cache dirs, log files, OS junk files, prior test/session-report directories) rather than hardcoding this specific project's directory names. `.claude/worktrees` itself is always excluded — a generic "copy everything ignored" pass would otherwise recursively pull every existing worktree into the new one.

**Decision: kept as a Simple Workflow, not Complex.** SKILL.md fits comfortably inline (~60 lines of actual workflow body) with one script doing the deterministic heavy lifting. No `references/` carve-out needed.

**Decision: no `customize.toml`.** The one thing a team might plausibly want to override — extra exclude patterns — is already exposed as a script CLI flag (`--exclude`) that the agent can pass ad hoc based on what the user asks for in the moment. Didn't add a persistent customization surface for a single-flag override; revisit if teams start wanting a standing per-project exclude list.

**Rejected: verifying copied environments with project-specific commands (e.g. `import fastapi`, `vite --version`).** Those were the exact spot-checks run live in the source session, but hardcoding them would make the skill only work for this one project's stack. SKILL.md instead states the outcome ("invoke a binary or interpreter the copy just placed") and lets the executing agent pick the actual command based on what it finds in the destination.

**Location note.** Written directly to the `main` checkout, not the `epic-32-continue` worktree this session was running in — this is general-purpose tooling, not epic-32 story work, and the operator asked for it to land on `main` specifically (committed on its own, without pulling in unrelated uncommitted work from a different landing-page redesign in progress on `main`).
