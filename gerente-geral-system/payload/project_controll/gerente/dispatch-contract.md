# Disk-marker dispatch contract (Story E8.4)

Story E8.4 (`ideias/sistema-artifacts/E8-4-contrato-despacho.md`), PRD 00 FR-8 (+ the
Sonnet side of FR-7), `ideias/epics.md` Epic E8. This document is the canonical contract
for the interface through which the Gerente Geral (`.claude/agents/gerente-geral.md`,
phases "despachar"/"revisar") hands off **one unit of work** (epic, multi-epic — once the
E10 supervisor exists —, or a standalone Ticket via `trilha: rapida|spec|correct-course`)
to the Execution Orchestrator and collects the **result** back. Same file-mediated
dispatch pattern already proven in `_bmad/custom/bmad-code-review.toml` (Epic E2 — the
code-review deadlock "kill"): a **payload** file + an empty
**completion marker**, written last. Script: `scripts/gerente_dispatch.py`
(stdlib-only, `--help` on each subcommand for the full flag reference).

## Why a disk marker, never a return value

A real execution dispatch (`bagual-epic-runner` for a whole epic, for instance) can take
a long time and cross a **context compaction** of the Gerente's session midway through —
if the result only existed as a return value from the `Agent` tool held in the
conversation's memory, it would vanish along with the compacted context. This document's
contract guarantees the dispatch is **reconstructible purely from disk**: even if the
Gerente's session is entirely lost and reopened from scratch, a new activation can, just
by looking at `project_controll/gerente/dispatches/` +
`estado-atual.yaml`, know which dispatch was in flight, whether it finished, and with
what result — without relying on any conversational memory.

## On-disk layout

```
project_controll/gerente/dispatches/{dispatch_id}/
  request.yaml    # written by `open-dispatch` — the unit, the Ticket(s), the trilha,
                   # the target worktree, the mapped skill, the executor model.
  result.yaml     # written by `close-dispatch` — outcome, verdict, pending items,
                   # evidence (commit/story-file/etc).
  DONE.marker     # written by `close-dispatch` AFTER result.yaml is already
                   # DURABLE on disk — the completion signal.
```

`dispatch_id` by convention: `dispatch-{YYYYMMDD-HHMMSS}-{hex8}` (generated by
`open-dispatch` when `--dispatch-id` is not passed explicitly). A `dispatch_id` is
**write-once**: `open-dispatch` refuses to reopen an id whose `request.yaml` already
exists (same rule as E2.1 for `review_run_dir` — never reuse a live/old run directory);
`close-dispatch` refuses to rewrite an already-present `result.yaml`/`DONE.marker`, unless
`--force` is explicit (not recommended — breaks the marker's write-once semantics).

## `request.yaml` schema

```yaml
schema_version: 1
dispatch_id: dispatch-20260711-030500-8a5d03a0
opened_at: "2026-07-11T03:05:00-03:00"
cycle_id: cycle-20260711-030000
tickets:
  - TCK-1720670000-ab12
unit: epic-E8
trilha: epic
worktree: null
skill: bagual-epic-runner
model: sonnet
status: aberto
note: null
```

- `tickets` is **always a list** (even for a single Ticket) — direct forward-compat with
  a multi-epic/multi-Ticket dispatch from the E10 supervisor, which this contract
  does **not** implement (it just doesn't close the door on it). Up through Story
  TCK-20260717131540-622d, the persona never dispatched more than one Ticket in
  parallel, so in practice the list always had exactly 1 item. Since that story, a single
  item continues to be the common case (shared root checkout), but real parallelism
  already exists when each Ticket gets its own isolated worktree — in that case, each
  parallel Ticket opens its OWN `dispatch_id`
  (a 1-item list each, one `open-dispatch` per worktree — this field keeps
  describing a single dispatch, not a batch; see `gerente-geral.md` § "Paralelismo de
  Tickets" in phase "3. despachar").
- `unit`: free-form identifier of the dispatched unit (`epic-E8`, `ticket:TCK-123`, or —
  once E10 exists — something like `multi-epic:[E10,E11]`).
- `trilha`: one of `rapida|spec|epic|wds|correct-course` (glossary from PRD 00 §3), the
  same trilha→skill table already used by the "despachar" phase of `gerente-geral.md`.
  🔴 **Since TCK-20260727143826-7573 (2026-07-27), this value is always Gerente/owner
  judgment, never a script call** — `project_controll/tickets/scripts/classify_trilha.py`
  is retired as a trilha decider (kept on disk for history, never deleted). The judgment
  criteria for `rapida` (pontual/simple) vs. `spec` (bigger than pontual, smaller than
  epic) vs. `epic` (multiple tickets, large/reiterated effect) live in the table at the
  top of `dispatch-and-review.md` step 1; `spec` and `epic` additionally require the
  `bmad-agent-pm` (John) never-headless plan-first gate — see
  `.claude/skills/bagual-gerente-geral/references/spec-epic-routing-execution.md`,
  mirroring the pre-existing `wds` never-headless gate right below.
- `skill`: the name of the skill actually invoked by the executor sub-agent
  (`bagual-epic-runner`, `bmad-quick-dev`, `bmad-create-story`+`bmad-dev-story`,
  `bmad-correct-course`, or the relevant `wds-*` pipeline).
- `model`: always `sonnet` by default (consolidates the executor side of FR-7 —
  "gerência em Opus, execução em Sonnet"). The field exists to make the contract
  self-describing, not because another value is expected today.

## `result.yaml` schema

```yaml
schema_version: 1
dispatch_id: dispatch-20260711-030500-8a5d03a0
closed_at: "2026-07-11T03:20:00-03:00"
outcome: sucesso
verdict: "epic E8 story E8-4 implementada, commit abc123"
pending_items:
  - ticket: TCK-1720670000-ab12
    note: "verificação final ainda não rodou"
evidence:
  commit: abc123
  story_file: ideias/sistema-artifacts/E8-4-contrato-despacho.md
closed_by: gerente-geral
```

- `outcome` ∈ `sucesso | falhou | pendencias` — never a loose boolean; `pendencias`
  exists specifically for the "finished but something is left to resolve" case (distinct
  from `falhou`, which is "didn't finish/broke").
- `pending_items`: list of `{ticket, note}` — what's missing, always tied to a Ticket
  when possible, so the "revisar" phase knows exactly what to record.
- `evidence`: free-form object (today: `commit`, `story_file`; can grow additively —
  `sprint_status_entry`, `pr_url`, etc. — without breaking existing readers, which only
  read the keys they know).

## The order guarantee — the core of the contract

`close-dispatch` always executes, in this order, and never reverses it:

1. `write_atomic(result.yaml, ...)` — blocks until the file is **durable** (temp +
   flush + fsync + `os.replace`, the same primitive from `_bmad/scripts/memlog.py` reused
   throughout Story E8.2).
2. **Only then** `write_atomic(DONE.marker, ...)`.

Practical consequence: **a reader must never observe `DONE.marker` without a complete
and valid `result.yaml` behind it.** If the process running `close-dispatch` dies between
steps 1 and 2 (e.g. the Gerente's own session being interrupted mid-call),
`DONE.marker` simply never comes to exist — the dispatch is correctly
detectable as an **orphan** (see § Orphan detection below), never as a false-success
with an incomplete result. `read-result` also guards against the theoretically
impossible-but-verified case (`DONE.marker` present and `result.yaml` missing/unreadable
due to some external corruption) by explicitly treating it as inconsistent — never as
silent success.

## DUAL completion detection (same lesson as E2.2/F5)

Migrating the result's transport to a file + marker **is not, by itself, sufficient**
— the lesson from E2.2 (documented in `_bmad/custom/bmad-code-review.toml`) is that the
root of the problem is never *where* the result is written, it's *how the dispatcher
knows the dispatched work finished*. Relying only on `DONE.marker` (a loop that keeps
re-checking the disk until the file appears) would trade a deadlock for a silent HANG:
if the executor sub-agent dies before calling `close-dispatch`, no disk poll would ever
finish.

For that reason, detecting a dispatch's completion combines TWO signals, in this order,
never interchangeable:

1. **PRIMARY / the trigger for when to look — the `<task-notification>` (default
   since Story TCK-20260717131540-622d, replaces the foreground return of
   E8.1-E8.4).** The persona (`gerente-geral.md`, "despachar" phase) spawns the executor
   sub-agent in **background** (`run_in_background: true`) and returns control
   IMMEDIATELY — it does not block waiting for the return. The trigger that fires the
   "revisar" phase **for that specific `dispatch_id`** stops being "the same turn in
   which the dispatch was opened" and becomes **when that dispatch's notification
   arrives** — success, failure, timeout, or the sub-agent's death all produce a
   notification; it is this now-asynchronous signal that replaces the old synchronous
   block. For the case where the Gerente's session ends/restarts BEFORE any
   notification arrives (session loss, end of cycle, next wake) — the mechanism below (2)
   plus `list-inflight`/`reconcile` (E8.2/E8.4, already run in step 0 of the
   "Ativação" of `gerente-geral.md`) guarantees the dispatch remains reconstructible
   purely from disk, without relying on any notification ever having reached this
   specific session.
2. **SECONDARY / payload — the `DONE.marker`, checked ONLY after (1) has signaled that
   the dispatch finished (the notification arrived, OR a subsequent activation is
   reconciling via `list-inflight`).** At this point, and only at this point,
   `read-result` is called: if `done: true`, `result.yaml` is the trusted payload
   (because of the order guarantee above). If the notification arrived (or the dispatch
   was found via `list-inflight`) but `done: false` (marker absent) — the case "the
   sub-agent signaled completion but never called `close-dispatch`" — this is treated
   **exactly as a failure**: the persona calls `reconcile-orphan-dispatch` for
   diagnosis and the Ticket moves to an explicit state (see § A Ticket never stays
   silently "concluido" below), never assumed a success.

`DONE.marker` is never, under any circumstance, used as the sole signal or
checked-first — and the persona never enters a loop that re-checks the disk waiting
for the marker to appear without (1) having already fired (notification received or
cycle/wake reconciliation in progress). This is exactly the hang pattern this section
exists to exclude (same guard phrasing as E2.2, applied here to the execution dispatch
instead of the code-review's 3 layers) — what the background-by-default changes is not
the ban on polling, only that "signal (1)" arrives through an asynchronous channel
(notification) instead of a synchronous tool return.

**Gerente level vs. nested sub-agent — a distinction this default NEVER erases:** the
background-by-default above is exclusively the Gerente's OWN dispatch, at the topmost
level (the one that receives the completion notification via the harness). An executor
sub-agent the Gerente dispatched remains forbidden from, in turn, spawning children in
background without waiting for them in the same turn — see § "Regra E19.1" right below,
which is exactly this rule for the lower level and doesn't change in this story.

### Regra E19.1 — the executor resolves in ONE foreground turn; no `idle` sub-tree left in flight

The contract above assumes the Gerente-level PRIMARY signal (the completion
notification, or — for a nested sub-agent spawned in foreground — the direct return of
the `Agent` tool) **always resolves cleanly** — success, failure, or death. The first
live cycle (`cycle-20260713-202850`,
Epic 38 dispatch) exposed a third case that breaks this premise: the executor spawned a
sub-flow that, by design, confirms via **disk markers** and doesn't block on the
return — and that sub-tree went **quiescent**, causing the executor's turn to come back `idle`
(neither success nor failure, `done: false`) instead of reaching `close-dispatch`. The
Gerente needed 3 resumption hops and a manual cut; the quota burned invisibly because
`close-dispatch --tokens-used` (the mechanical accounting) is exactly the call that
never happened.

Normative rule, inherited by any dispatched skill:

1. **A dispatched executor reaches `close-dispatch` as its LAST foreground action, in
   the SAME turn.** It is forbidden for an executor to end its turn leaving a
   background/idle sub-tree in flight. If it spawns any gate or sub-flow that confirms
   via marker (a disk-marker-confirmed sub-flow is the canonical case), that gate **has to
   resolve to a terminal verdict in-turn** (block until the verdict marker exists on disk)
   **before** the executor returns — never "still exploring", never `run_in_background`
   without the executor waiting for it in the same turn.
2. **An executor turn that comes back `idle`/without a verdict is treated as a failure**,
   identical to the `done: false` case in (2) above: `reconcile-orphan-dispatch` + Ticket
   in an explicit state, never assumed a success, never a re-hop loop babysitting the tree.
3. The mechanical enforcement of this rule lives at the execution layer: any dispatched
   skill that spawns a marker-confirmed sub-flow must do so in foreground and guard
   "no verdict → HALT" (block until the terminal marker exists on disk, never return
   idle). This contract is the normative statement those edits enforce. Complementarily,
   Story E19.2 closes the invisible-quota window even if
   a dispatch still escapes as an orphan (dispatch-in-flight estimate in
   `gerente_quota.py check`).

## Integration with `estado-atual.yaml` (E8.2) — who owns what

`gerente_dispatch.py` **never** writes `estado-atual.yaml` directly — the sole owner of
the entire file remains `gerente_state.py write-snapshot` (the same decision already made
for `quota-ciclo.json` in Story E8.3, documented in `decisions.md`: two writers of the
same whole file is a real source of lost-update bugs, because `write-snapshot`
rewrites the whole document on every call, it doesn't do an incremental append).

Instead:

1. `open-dispatch` returns a `dispatch_entry` (JSON) — exactly the format the
   `dispatches[]` field of `estado-atual.yaml` already expects (`{ticket, unit, trilha,
   worktree, status, started_at}`, see README.md § Schema) **plus** the new
   `dispatch_id` field (additive, no `schema_version` bump). The persona includes this
   object in the NEXT `write-snapshot --dispatches-json` call (which was going to run
   anyway).
2. **`dispatch_entry` deliberately does NOT include the full `tickets` list** — a real
   finding from this story's self-review: `estado-atual.yaml`'s mini YAML serializer
   (`dump_estado`/`dump_flat_dict_item`) only supports a dict-of-scalars at **1 level**; a
   nested list inside a `dispatches[]` item would be incorrectly serialized as the
   *string* `"['TCK-1']"` instead of a real list (reproduced and fixed in this story — see
   the Change Log). The full ticket list already lives, authoritative, in
   `request.yaml`; `estado-atual.yaml` carries only `ticket` (singular, primary, for
   quick human reading) + `dispatch_id` (the pointer).
3. `gerente_state.py::reconcile` (E8.2) was EXTENDED in this story: for each dispatch in
   the snapshot that carries a `dispatch_id`, it (a) resolves the full ticket list by
   reading `dispatches/{dispatch_id}/request.yaml` when available (preferring it over the
   snapshot's `tickets`/`ticket`, which may be stale) and (b) checks whether
   `dispatches/{dispatch_id}/DONE.marker` exists — its absence becomes yet another
   orphan reason in the `orphans[].reasons` list, side by side with the pre-existing
   cross-check against `board.yaml`/worktree. The two mechanisms (E8.2's crash-recovery,
   E8.4's marker) **converge in the same `reconcile`**, they are not diverging parallel
   paths.

## A Ticket never silently stays `concluido` on a dispatch that fails

When a dispatch closes with `outcome: falhou` or `outcome: pendencias`, or when it is
detected as an orphan (no `DONE.marker`), the "revisar" phase of `gerente-geral.md`
**never** invokes `bagual-tickets` to mark the Ticket as `concluido`. Instead:

- `outcome: falhou` → the Ticket goes back to `triado` (with a note on the reason) or
  `precisa-de-info` (if the blocker is informational), via `bagual-tickets` — never
  editing `board.yaml` by hand.
- `outcome: pendencias` → the Ticket stays in a state that reflects "almost there" (e.g.
  it only keeps `em-implementacao` if a clear continuation is already planned for the
  next cycle, or `triado` with the `pending_items` annotated) — the exact decision is
  the persona's, but `concluido` is always off the table until the `pending_items` are
  resolved.
- Orphan dispatch (no `DONE.marker`, reported by `reconcile-orphan-dispatch` or E8.2's
  `reconcile`) → same treatment as `falhou`: the Ticket goes to an explicit state,
  never left stuck forgotten in `em-implementacao` nor promoted to `concluido` by
  assumption.

## Closed scope in the parallel dispatch prompt (Post-incident rule, Epic 18, 2026-07-23)

**Origin incident:** Epic 18 (2026-07-23) suffered a **double dispatch** — a paused
`bagual-epic-runner` was resumed with a plain "continue" while individual stories from
the same epic were already running in parallel outside of it, producing the same story
implemented twice and uncommitted work at the root blocking a sibling agent's merge.
Root causes: (1) the dispatch prompt ("implement Story X") never said "and only that one,
stop" — the agent assumed the whole epic; (2) "continue" to a paused agent doesn't
reassert scope; (3) the whole-epic orchestrator and individual per-story dispatches were
alive at the same time, with no mutual exclusion. See
`wiki/ledger/anti-pattern/despacho-sem-escopo-fechado-duplo-despacho.md` for the full
anti-pattern record (Ticket `TCK-20260723153000-9f21`).

**Normative rule — every PARALLEL dispatch prompt (more than one executor sub-agent in
flight at the same time in the same checkout/worktree-pool) MUST:**

1. **Open with an explicit CLOSED scope:** "deliver ONLY this unit [Ticket/story/
   epic], then STOP and return; don't start the next one even if the epic/backlog lists
   more". Never a prompt that leaves the unit's boundary implicit or assumed by the
   agent.
2. **Declare which sibling agents are running RIGHT NOW and their territories** (files/
   directories/worktree of each) — every parallel dispatch explicitly cites what the
   other dispatches alive in the same cycle are touching, so the agent knows what to
   avoid colliding with.
3. **Forbid work at the root when worktrees are in use**: if the agent finds someone
   else's uncommitted file at the root of the shared checkout, the instruction is **don't
   touch it, report it** — never try to "clean it up" or claim ownership of what isn't
   theirs.
4. **When RESUMING a paused agent, reassert the exact scope** — never just "continue".
   The resume prompt repeats the closed unit (rule 1) and, if applicable, the updated
   list of sibling agents (rule 2), because the cycle's state may have changed while the
   agent was paused.
5. **Never keep a whole-epic orchestrator (`bagual-epic-runner`) and individual
   per-story dispatches of the SAME epic alive at the same time.** Pick one of the two
   modes per epic, not both simultaneously — it is exactly this overlap that caused the
   origin incident's double dispatch.

This section is referenced (not duplicated) by `.claude/agents/gerente-geral.md` phase "3.
despachar" — any dispatch prompt the persona builds follows the 5 rules above
before spawning the `Agent` tool.

## Forward-compat with the multi-epic supervisor (E10) — what this contract does NOT do

This story delivers the contract for **today's sequential** Execution Orchestrator
(`bagual-epic-runner` single-epic, `workflow.md`/`story-processor.md`) — the real
multi-epic supervisor (PRD 03, Epic E10: graph by file disjunction, dependency
sequencing, per-Track failure isolation) **does not exist yet**. The contract was
designed so it doesn't need to change when E10 arrives:

- `tickets` is already a list (not a hardcoded singular) — an E10 multi-epic dispatch
  just needs to pass more than one item in `--tickets-json`; no schema migration.
- `unit` is a free-form string — it already accepts `epic-E8` today; E10 can pass
  `multi-epic:[E10,E11]` or a graph representation without breaking the parser (which
  doesn't interpret `unit`, only propagates it).
- One `dispatch_id` per dispatched unit generalizes without change to "several dispatches
  in flight simultaneously" — `list-inflight`/`reconcile-orphan-dispatch` already operate
  per individual `dispatch_id`, they don't assume there's only one dispatch at a time
  (the restriction "never more than one Ticket in parallel" was a PERSONA rule in E8.1,
  not this contract's, and has already been partially relaxed by Story
  TCK-20260717131540-622d — conditional parallelism via isolated worktree, one
  `dispatch_id` per Ticket/worktree, see
  `gerente-geral.md` § "Paralelismo de Tickets". E10 still has room to go further than
  this — automatic/orchestrated parallelism by dependency graph without requiring the
  Gerente's manual judgment about file overlap — but the script already imposes no
  restriction of its own either before or after this story).
- **What E10 NEEDS to add** (out of scope here, named so it isn't reimplemented too
  early): real execution parallelism (concurrent spawns, not just the schema accepting
  multiple tickets), per-Track failure isolation (one dispatch failing shouldn't block
  the others), and possibly a partial `close-dispatch` (a Track finished within a larger
  multi-epic dispatch still in flight) — this contract today only models "open" → "a
  single terminal close", not partial closes.

## Findings from adversarial self-review (fixed in this story)

- **Compaction gap between `open-dispatch` and the following `write-snapshot`** — the
  most important finding of this story. `gerente_state.py::reconcile` (E8.2) only sees
  dispatches already recorded in `estado-atual.yaml`'s `dispatches` array. If a context
  compaction happens exactly between `open-dispatch` (which only writes `request.yaml`)
  and the following `write-snapshot --dispatches-json` (which would record the
  `dispatch_entry`), the dispatch ends up with a `request.yaml` on disk and no
  `DONE.marker`, but `reconcile` reports `needs_attention: false` — a real false
  negative, reproduced and confirmed in `test_gerente_dispatch.py` [11a]. **Fixed** by
  wiring `gerente_dispatch.py
  list-inflight` (which scans `dispatches/` directly, without depending on
  `estado-atual.yaml`) as an UNCONDITIONAL check in the Ativação of `gerente-geral.md`
  (step 0, always, even when `detect-crash` didn't fire) — see `test_gerente_dispatch.py`
  [11b] proving that `list-inflight` finds the same dispatch that `reconcile` alone
  missed. This is what makes the contract **truly reconstructible purely from disk**
  (not just in most cases) — without this unconditional check, a dispatch opened and
  immediately followed by a compaction would be invisible to ANY recovery mechanism, the
  opposite of what the story asks for.
- **`dispatch_id` as a path component without validation (path traversal risk)** — an
  explicit malformed `--dispatch-id` (e.g. `../../etc`) would be used directly to build
  `root / "dispatches" / dispatch_id`, potentially escaping the intended directory.
  The AUTO-GENERATED id is safe by construction (`dispatch-{timestamp}-{hex8}`), but the
  explicit-override path (used by resumptions/tests) wasn't validated. **Fixed**:
  `_validate_dispatch_id` (regex `^[A-Za-z0-9_.-]+$` + explicit rejection of `.`/`..`,
  which would pass the character class) is called at the start of `open-dispatch`,
  `close-dispatch`, `read-result`, and `reconcile-orphan-dispatch` — proven in
  `test_gerente_dispatch.py` [10a]-[10e].
- **Round-trip of a pure-scalar list in `parse_estado`** — pre-existing bug in
  `gerente_state.py` (E8.2), never exercised before because no schema prior to E8.4
  used a pure-scalar list (`tickets: [- TCK-1]`) inside the mini-YAML —
  `parse_estado` treated EVERY list item as a dict, producing `[{"TCK-1": None}]` instead
  of `["TCK-1"]`. **Fixed** in `gerente_state.py::parse_estado` (decides
  dict-list vs. scalar-list by the block's first item, checking whether it has the
  shape `bare-identifier: value`) — see `test_gerente_dispatch.py` [2a] and the full
  `test_gerente_state.py` regression (28/28 still green).
- **Nested list inside a `dispatches[]` item of `estado-atual.yaml`** —
  discovered while trying to include `tickets` (a list) in the `dispatch_entry` returned
  by `open-dispatch`: the serializer (`dump_estado`/`dump_flat_dict_item`) only supports
  a dict-of-scalars at 1 level; a nested list turned into the literal string
  `"['TCK-1']"`. **Fixed** by removing `tickets` from `dispatch_entry` (the full list
  already lives in `request.yaml`; `estado-atual.yaml` carries only the singular
  `ticket` + `dispatch_id` as a pointer) — see § Integration above.
- **Result-before-DONE order** — verified not just by reading the code (two sequential
  `write_atomic` calls, each blocking until its own atomic rename) but by an actual
  comparison of the two files' `mtime_ns` on disk (`test_gerente_dispatch.py`
  [3d]).
- **Residual concern, accepted without a fix**: `estado-atual.yaml` still doesn't validate
  the `dispatch_id` value (or any other field) when embedded via
  `write-snapshot --dispatches-json` by the persona — the same confidence level already
  applied to every other field in that array (`ticket`, `worktree`, etc.) since E8.2. It's
  not a real risk vector in this system (a single trusted agent operating locally, not an
  adversarial network surface) — validating there would be a bigger scope than this
  story and inconsistent with the trust model already established in the rest of the
  module.

## CLI reference

```
python3 project_controll/gerente/scripts/gerente_dispatch.py open-dispatch \
  --root project_controll/gerente [--dispatch-id ID] --cycle-id ID \
  --tickets-json '["TCK-123"]' --unit epic-E8 --trilha rapida|spec|epic|wds|correct-course \
  [--worktree PATH] --skill bagual-epic-runner [--model sonnet] [--note STR]

python3 project_controll/gerente/scripts/gerente_dispatch.py close-dispatch \
  --root project_controll/gerente --dispatch-id ID --outcome sucesso|falhou|pendencias \
  --verdict STR [--pending-json '[{"ticket":"TCK-1","note":"..."}]'] \
  [--evidence-json '{"commit":"...","story_file":"..."}'] [--closed-by STR] [--force]

python3 project_controll/gerente/scripts/gerente_dispatch.py read-result \
  --root project_controll/gerente --dispatch-id ID

python3 project_controll/gerente/scripts/gerente_dispatch.py list-inflight \
  --root project_controll/gerente [--cycle-id ID]

python3 project_controll/gerente/scripts/gerente_dispatch.py reconcile-orphan-dispatch \
  --root project_controll/gerente --dispatch-id ID [--board-path PATH]
```

## How the persona uses this (see `.claude/agents/gerente-geral.md` phases 3-4)

**"despachar" phase:**
1. `open-dispatch` with the `trilha`/Ticket(s) chosen in the "priorizar" phase → stores
   `dispatch_id` and `dispatch_entry_json`. A parallel Ticket via an isolated worktree
   (see `gerente-geral.md` § "Paralelismo de Tickets") repeats this step once per Ticket,
   each with its own `--worktree`.
2. Calls `write-snapshot --dispatches-json '[...]'` including the freshly opened
   `dispatch_entry` (together with any other dispatches from the same cycle still in
   flight).
3. Spawns the `Agent` tool (**`model: "sonnet"`**, **background by default**
   `run_in_background: true` — Story TCK-20260717131540-622d, replaces the foreground of
   E8.1-E8.4) with a prompt instructing the sub-agent to: (a) invoke the skill mapped by
   the `trilha` (the same trilha→skill table already documented in `gerente-geral.md`),
   passing the Ticket's content; and (b) as its LAST action, call `close-dispatch` with
   this dispatch's `--dispatch-id` and the actually observed outcome.
   🔴 **Dispatch with an isolated worktree (TCK-20260718135718-c49f):** when this
   dispatch uses a pool worktree (`--worktree`, see `gerente-geral.md` § "Paralelismo de
   Tickets"), `close-dispatch` is NOT truly the last action — the sub-agent still has
   to **merge the worktree's branch into `dev` from the root checkout** BEFORE calling
   `pool_manager.py return`. Returning the worktree before the merge is forbidden:
   `return` hard-resets the worktree's own branch against `--base-branch`, orphaning any
   not-yet-merged commit — already reproduced twice live (see
   `wiki/nota-operacional/worktree-return-hard-resets-branch-merge-before-returning.md`).
   `pool_manager.py return` now mechanically refuses this scenario (checks for commits
   unreachable from `--merge-target`, default `dev`; `--force-discard` is the explicit
   escape hatch) — but the merge step remains the correct contract, not a safety net to
   rely on the tool's blocking for. The persona **returns control immediately**
   after the spawn — it does not wait for the return in this turn.

**"revisar" phase — runs when that `dispatch_id`'s notification arrives (this may be a
turn much later, or even a future activation):**
4. The `<task-notification>` for the dispatch has already arrived — the PRIMARY signal
   (replaces the old "return of the Agent tool" — same role, now asynchronous).
5. `read-result --dispatch-id ID`. If `done: true`, uses `result.yaml` as the source of
   truth (outcome/verdict/pending_items/evidence). If `done: false` despite the
   notification having already arrived, calls `reconcile-orphan-dispatch --dispatch-id ID`
   for diagnosis and treats it as a failed dispatch.
6. Records the Ticket in the observed state (never `concluido` on a `falhou`/
   `pendencias`/orphan dispatch — see section above), via `bagual-tickets`.

**If the cycle (or the session) ends before some notification arrives:** this is
expected with background as the default, not an error — the dispatch remains
trackable purely via disk (`estado-atual.yaml.dispatches[]` +
`dispatches/{dispatch_id}/`). The next
cycle/wake reconciles via `list-inflight`/`reconcile-orphan-dispatch` in step 0 of the
"Ativação" of `gerente-geral.md`, exactly as it already reconciles any dispatch
surviving a context compaction.
